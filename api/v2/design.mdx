<Note>
  This page is a draft for product and engineering review. It describes the
  proposed API v2 contract, not the current implementation.
</Note>

API v2 is the place for breaking API improvements and new public resources.
The first phase focuses on public booking-form use cases and public catalog data.

## Review goals

Use this proposal to agree on the product-facing contract before implementation:

- How API versions are exposed and how API v1 is deprecated later.
- How clients authenticate public requests.
- How list endpoints paginate.
- How localized fields are requested and returned.
- How IDs, currencies, money values, dates, and errors are shaped.
- How image and thumbnail fields are shaped.
- How the new `room-types` resource should work.
- How API v1 clients can migrate safely.

## Resolved decisions

These decisions are part of the current proposal.

| Area | Decision |
| --- | --- |
| Versioning | Keep major API versions in the URL path, such as `/api/v1` and `/api/v2`. |
| Naming | Use `camelCase` for query parameters and JSON fields. |
| Paths | Use plural resource paths such as `/hotels`, `/room-types`, and `/visit-types`. |
| IDs | Use ObjectId string values as public `id` values in API v2. |
| Legacy IDs | Do not expose legacy numeric API v1 IDs in API v2. |
| Authentication | Use `X-SpaPortal-Public-Key` for public API v2 endpoints. |
| Secret keys | Defer secret-key and server-to-server endpoints to a later phase. |
| Query credentials | Do not support credentials in query parameters. |
| Localization | Use BCP 47 language tags in `Accept-Language`; do not support `?language=...`. |
| Missing language | Return all supported language keys when `Accept-Language` is omitted. |
| Locale metadata | Add `GET /api/v2/locales` to list supported locale tags and fallback metadata. |
| Pagination | Use cursor pagination for public list endpoints. |
| Totals | Return `pagination.total` by default for public catalog/list endpoints. |
| Money | Use `amountMinor`, `currency`, and `currencyExponent`. |
| Currency filter | Support `currency` only on endpoints that return prices. |
| Images | Use `images[]` with `url` and `thumbnailUrl` for image collections. |
| Room types | Add `room-types` as a first-class public API v2 resource. |
| Room type prices | Return `lowestPrices` by default on room type endpoints. |
| Room type booking URLs | Return `bookingUrl` by default on room type endpoints. |
| Hotel room types | Paginate `/hotels/{hotelId}/room-types` from the beginning. |

## Open review points

Product and engineering should still confirm:

- Which API v1 endpoints are migrated into API v2 first.
- Which API v1 responses should gain Mongo `_id` values first to support
  migration.
- Which additional API v1 endpoints should migrate into API v2 after
  `POST /api/v2/calendar/dates/bulk`.
- The exact API v1 deprecation and sunset dates. API v1 should not be deprecated
  until API v2 covers the required production use cases.
- The future list of secret-key endpoints and scopes. API v2 phase one does not
  include secret-key endpoints.
- The room type details listed in the room type section.

## Versioning strategy

Use major versions in the URL path.

```txt
https://spaportal.cz/api/v1
https://spaportal.cz/api/v2
```

```txt
https://staging.spaportal.cz/api/v1
https://staging.spaportal.cz/api/v2
```

Do not version API v2 through hostnames, query parameters, or media type
headers. Path versioning is explicit, easy to test, and already matches the
existing SpaPortal API structure.

Additive changes can be made inside the same major version:

- New optional response fields.
- New endpoints.
- New optional query parameters.
- New enum values when clients can safely ignore unknown values.

Breaking changes require a new major version:

- Removing or renaming fields.
- Changing field types.
- Changing ID semantics.
- Changing authentication requirements.
- Changing pagination or error shapes.

API v1 remains the current production API until API v2 covers the required
production integration use cases.

Recommended API v1 deprecation plan:

1. Keep API v1 fully supported while API v2 is incomplete.
2. Add Mongo `_id` values to selected API v1 responses as a migration bridge.
3. Publish API v2 endpoint coverage and migration notes as endpoints are added.
4. Move API v1 into maintenance mode only after API v2 supports the required
   production flows.
5. Announce API v1 deprecation with a concrete sunset date before sending
   deprecation headers.
6. Use at least a 12-month migration window after the deprecation announcement
   unless product explicitly approves a shorter window for low-risk clients.

When API v1 is deprecated, responses can include `Deprecation` and `Sunset`
headers and a documentation link to the migration guide.

## Naming

API v2 uses `camelCase` in query parameters and JSON payloads.

```http
GET /api/v2/hotels?destinationId=66f16191f739705faa020768&limit=50
```

API v2 does not use API v1 `snake_case` names in the final contract.

```http
GET /api/v2/hotels?destination_id=1&max=50&offset=0
```

Modern APIs are not unanimous here. Google-style HTTP/JSON APIs use a camel-case
JSON ecosystem, while Stripe is a mature API that uses `snake_case`. SpaPortal
API v2 chooses `camelCase` because it is a new JSON contract in a TypeScript and
browser-client ecosystem.

The current `POST /api/v2/calendar/dates/bulk` endpoint uses `camelCase` field
names and ObjectId string IDs.

## Authentication

API v2 separates browser-safe public identification from future server-side
authorization.

Send public keys in a dedicated header:

```http
X-SpaPortal-Public-Key: pk_live_...
```

Public keys identify the channel and scope the request. They are not secrets.

Use public keys for endpoints that a public booking form must call:

- Catalog data.
- Availability data.
- Pricing data.
- Non-sensitive booking-form operations.

The first API v2 phase is public-key only. Secret keys and secret-key scopes are
reserved for a later server-to-server API phase.

Do not send API v2 credentials in query parameters.

## IDs

API v2 uses ObjectId string values as public `id` values.

```json
{
  "id": "66f16191f739705faa020768",
  "name": {
    "cs-CZ": "Pawlik"
  }
}
```

API v2 does not expose Mongo-style `_id` field names and does not expose legacy
numeric API v1 IDs.

For migration, API v1 can later add `_id` fields while keeping its existing
numeric `id` fields. API v2 should expose that same ObjectId value as `id`.

Every detail lookup must still be scoped through the authenticated channel and
company context. Knowing an ID must not grant cross-tenant access.

## Pagination

API v2 list endpoints use cursor pagination.

```http
GET /api/v2/room-types?limit=25&cursor=eyJzb3J0VmFsdWUiOi...
```

Response:

```json
{
  "data": [],
  "pagination": {
    "limit": 25,
    "nextCursor": null,
    "hasMore": false,
    "total": 372
  }
}
```

Use these parameters:

| Parameter | Default | Maximum | Description |
| --- | ---: | ---: | --- |
| `limit` | `25` | `100` | Number of records to return. |
| `cursor` | - | - | Opaque cursor from the previous page. |
| `sort` | endpoint-specific | - | Allowlisted sort key. |

MongoDB is compatible with cursor pagination when every list endpoint uses a
stable, indexed sort. Do not treat the public cursor as a raw Mongo `_id`.
Return an opaque cursor that contains the last sort value and the last ObjectId.

Mongo ObjectId values are not random hashes. They include a timestamp component
and can be used for stable creation-order pagination, but API v2 should not
depend on ObjectId ordering for every product sort.

For the default creation-order sort, implementation can use ObjectId internally:

```json
{
  "sort": "createdAt:desc",
  "lastId": "66f16191f739705faa020768"
}
```

For non-unique sorts, always add ObjectId as a tie-breaker:

```json
{
  "sort": "name:asc",
  "lastSortValue": "Pawlik",
  "lastId": "66f16191f739705faa020768"
}
```

The query must continue after both values, for example `name > lastSortValue`
or `name == lastSortValue and id > lastId` for ascending sorts. Add compound
indexes that match the supported filters and sort keys.

Changing filters, `sort`, `Accept-Language`, or `currency` should require a new
pagination sequence. Cursors may include these request options internally and
return `invalid_request` when they do not match the current request.

Return `pagination.total` by default for public catalog/list endpoints such as
hotels, destinations, visit types, room types, tags, and loyalty programs.

Future high-volume or sensitive endpoints, such as reservations or payments, can
make total counts opt-in or omit them.

## Localization

Use `Accept-Language` to request localized fields.

```http
Accept-Language: de-AT,de;q=0.9,en;q=0.8
```

Clients can send this header in several valid forms.

For a simple API integration that wants exactly one locale:

```http
Accept-Language: de-AT
```

For a client that wants Austrian German first, then generic German, then
English:

```http
Accept-Language: de-AT,de,en
```

For a browser-like preference list with explicit priorities:

```http
Accept-Language: de-AT,de;q=0.9,en;q=0.8,cs-CZ;q=0.7
```

The `q` value is optional. It means quality or priority. If omitted, the value
is treated as `q=1.0`. API clients can usually send a single locale or a short
ordered list without `q`. Browsers often send a longer list with `q` values
automatically.

API v2 uses canonical BCP 47 language tags for public request and response
locale keys. Use hyphenated tags such as `cs-CZ`, `de-DE`, `de-AT`, `de-CH`,
`en`, and `ru`.

Do not expose underscore locale keys such as `cs_CZ` in API v2 responses. If
current storage uses legacy keys, map them at the API boundary.

Initial supported public tags are:

- `cs-CZ`
- `de`
- `en`
- `ru`

Future regional variants can be added without changing the response shape:

- `de-DE`
- `de-AT`
- `de-CH`

Localized fields remain objects keyed by language.

```json
{
  "name": {
    "de-AT": "Franzensbad",
    "de": "Franzensbad",
    "en": "Frantiskovy Lazne"
  }
}
```

For example, a future response with all German regional variants can look like
this:

```json
{
  "description": {
    "de": "Kurhotel in Franzensbad.",
    "de-DE": "Kurhotel in Franzensbad.",
    "de-AT": "Kurhotel in Franzensbad.",
    "de-CH": "Kurhotel in Franzensbad.",
    "en": "Spa hotel in Frantiskovy Lazne.",
    "cs-CZ": "Lazensky hotel ve Frantiskovych Laznich."
  }
}
```

The regional values can be identical at first. They should exist as separate
keys only when product needs separate wording, legal text, market-specific
labels, or SEO content for Germany, Austria, and Switzerland.

If `Accept-Language` is provided, parse it using normal HTTP language negotiation
rules, including `q` weights. Unsupported locale tags are ignored. They should
not produce an error and should not be returned in localized response objects.
Return the matching supported locale keys in preference order, de-duplicated
after fallback matching.

When resolving a requested locale, match in this order:

1. Exact requested tag, such as `de-AT`.
2. Base language fallback, such as `de`.
3. Configured project default, such as `cs-CZ`.

Do not return `406 Not Acceptable` when none of the requested locales are
supported. Return the default locale instead.

Examples:

| Request | Returned locale keys |
| --- | --- |
| `Accept-Language: de-AT` | `de-AT` |
| `Accept-Language: de-AT,de,en` | `de-AT`, then `de`, then `en` |
| `Accept-Language: de-AT,de;q=0.9,en;q=0.8` | `de-AT`, then `de`, then `en` |
| `Accept-Language: de-CH,de;q=0.9` | `de-CH`, then `de` |
| `Accept-Language: de-DE` when only `de` exists | `de` |
| `Accept-Language: fr-FR,en;q=0.8` when French is unsupported | `en`, then default `cs-CZ` if `en` is missing |
| `Accept-Language: fr-FR,it-IT` when both are unsupported | default `cs-CZ` |
| no `Accept-Language` | all supported locale keys |

If `Accept-Language` is omitted, return all supported language keys. Do not
support `?language=...`.

Return `Content-Language` with the language keys included in the response. Also
return `Vary: Accept-Language` when the response differs by `Accept-Language`.

For heavy multilingual responses, keep the same object shape and return all
available canonical locale keys when `Accept-Language` is omitted. Do not create
parallel field names such as `nameDe`, `nameDeAt`, or `nameCs`.

Add a locale metadata endpoint so clients can discover supported tags and
fallbacks.

```http
GET /api/v2/locales
```

```json
{
  "data": [
    {
      "code": "cs-CZ",
      "name": "Czech (Czechia)",
      "default": true,
      "fallbackCode": null,
      "direction": "ltr"
    },
    {
      "code": "de-AT",
      "name": "German (Austria)",
      "default": false,
      "fallbackCode": "de",
      "direction": "ltr"
    },
    {
      "code": "de-DE",
      "name": "German (Germany)",
      "default": false,
      "fallbackCode": "de",
      "direction": "ltr"
    },
    {
      "code": "de-CH",
      "name": "German (Switzerland)",
      "default": false,
      "fallbackCode": "de",
      "direction": "ltr"
    }
  ]
}
```

This endpoint is not paginated unless the locale list becomes unexpectedly
large.

### Localization references

This proposal follows the same broad direction as these public standards and
APIs:

- [MDN: `Accept-Language`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Accept-Language) describes language tags such as `en-US`, `fr-CA`, and `sr-Latn`, including weighted `q` values.
- [MDN: BCP 47 language tag](https://developer.mozilla.org/en-US/docs/Glossary/BCP_47_language_tag) summarizes the web-standard locale tag format used for internationalization.
- [Contentful localization strategies](https://www.contentful.com/help/localization/field-and-entry-localization/) explicitly model regional language variants such as `de-DE`, `de-AT`, and `de-CH`, plus fallback behavior.
- [Phrase locales API](https://developers.phrase.com/en/api/strings/locales/list-locales) exposes locale `code` values such as `de-DE` and `en-GB`, and includes fallback locale metadata.
- [Localazy JSON localization](https://localazy.com/docs/cli/json-format/) supports multilingual JSON with locale codes and includes BCP output formatting.
- [Microsoft Translator languages API](https://learn.microsoft.com/en-us/rest/api/translator/translator/languages?view=rest-translator-v3.0) uses BCP 47 tags as language keys and localizes display names through `Accept-Language`.
- [Google Cloud Translation language support](https://docs.cloud.google.com/translate/docs/languages) uses region/script variants such as `zh-CN`, `zh-TW`, and `zh-HK` where variants matter.

## Money and currencies

Use ISO 4217 currency codes.

Money values use the smallest currency unit:

```json
{
  "amountMinor": 3150000,
  "currency": "CZK",
  "currencyExponent": 2
}
```

`currencyExponent` tells the client how many decimal places the currency uses.
For `CZK` and `EUR`, exponent `2` means `3150000` is `31500.00`.

For multi-currency fields, return a currency-keyed object:

```json
{
  "lowestPrices": {
    "CZK": {
      "amountMinor": 3150000,
      "currency": "CZK",
      "currencyExponent": 2,
      "unit": "personPerNight"
    },
    "EUR": {
      "amountMinor": 124000,
      "currency": "EUR",
      "currencyExponent": 2,
      "unit": "personPerNight"
    }
  }
}
```

Use `currency` only on endpoints that return prices, or where prices are part of
the response.

If `currency` is omitted, return all available currencies. If a supported
currency is explicitly requested and no price exists, return that currency with
`null`.

```json
{
  "lowestPrices": {
    "EUR": null
  }
}
```

Do not infer currency from `Accept-Language`. Do not implicitly convert prices.

## Dates and times

Use date-only strings for calendar dates and stay dates.

```json
{
  "dateFrom": "2026-04-01",
  "dateTo": "2026-04-30"
}
```

Use UTC timestamps for exact instants.

```json
{
  "createdAt": "2026-04-01T10:15:30.000Z"
}
```

Do not let browser or server local time zones change date-only values.

## Error shape

API v2 should use one error shape.

```json
{
  "error": {
    "code": "invalid_request",
    "message": "hotelId must be a valid ObjectId.",
    "details": [
      {
        "field": "hotelId",
        "code": "invalid_object_id"
      }
    ],
    "requestId": "req_..."
  }
}
```

Common error codes:

| Code | Meaning |
| --- | --- |
| `invalid_request` | The request is malformed or validation failed. |
| `missing_authentication` | The request did not include credentials. |
| `invalid_authentication` | The provided key is invalid. |
| `insufficient_scope` | The key is valid but cannot access the operation. |
| `not_found` | The resource was not found in the scoped context. |
| `conflict` | The request conflicts with current state. |
| `rate_limited` | The client exceeded a rate limit. |
| `internal_error` | An unexpected server error occurred. |

## Images and thumbnails

Use one image object shape across API v2.

```json
{
  "url": "https://spaportal-files.s3.eu-central-1.amazonaws.com/production/rooms/example.jpg",
  "thumbnailUrl": "https://spaportal-files.s3.eu-central-1.amazonaws.com/production/thumbnails/rooms/example.webp"
}
```

Image collections use `images[]`.

```json
{
  "images": [
    {
      "url": "https://spaportal-files.s3.eu-central-1.amazonaws.com/production/rooms/example.jpg",
      "thumbnailUrl": "https://spaportal-files.s3.eu-central-1.amazonaws.com/production/thumbnails/rooms/example.webp"
    }
  ]
}
```

Use `thumbnailUrl` in API v2, not `thumbnail_url`, because API v2 uses
`camelCase`. The product requirement for `images[]` with thumbnail URLs is still
covered by this schema.

Do not return a separate `primaryImage` field in API v2. If a frontend needs a
single preferred image, it can use the first item in `images[]`.

Use `null` for `thumbnailUrl` only when the original image exists but no
thumbnail is available. Use an empty `images` array when the resource has no
images.

## Room types

API v2 adds `room-types` as a first-class resource.

A room type is a category of room in a hotel. It is not a concrete room instance.
One hotel can have multiple room types.

### Endpoints

| Endpoint | Description |
| --- | --- |
| `GET /api/v2/room-types` | List room types across hotels available to the public key. |
| `GET /api/v2/room-types/{roomTypeId}` | Get one room type. |
| `GET /api/v2/hotels/{hotelId}/room-types` | List room types in one hotel. |
| `GET /api/v2/hotels/{hotelId}/room-types/{roomTypeId}` | Get one room type and verify it belongs to the hotel. |

All room type list endpoints are paginated.

### Relationship to hotels

Room type responses include `hotelId` by default.

```json
{
  "id": "66f16191f739705faa020770",
  "hotelId": "66f16191f739705faa020769"
}
```

Do not embed the full hotel object by default. Use `include=hotel` when a client
needs a compact hotel summary.

```http
GET /api/v2/room-types?include=hotel
```

### Query parameters

| Parameter | Type | Description |
| --- | --- | --- |
| `limit` | number | Cursor page size. Default `25`, maximum `100`. |
| `cursor` | string | Opaque cursor from the previous response. |
| `hotelId` | string | Filter to one hotel. |
| `destinationId` | string | Filter to room types in hotels assigned to a destination. |
| `visitTypeId` | string | Filter to room types compatible with a visit type. |
| `beds` | number | Filter to exact bed count. |
| `code` | string | Filter to one room type code. |
| `search` | string | Search localized category name and code, if supported. |
| `dateFrom` | string | Date-only value for availability and pricing filters. |
| `dateTo` | string | Date-only value for availability and pricing filters. |
| `availableOnly` | boolean | Return only room types with capacity in the date range. |
| `currency` | string | Filter returned price fields to one currency. |
| `include` | string | Supported value: `hotel`. |
| `sort` | string | Allowlisted sort key. |

### Response example

```json
{
  "data": [
    {
      "id": "66f16191f739705faa020770",
      "hotelId": "66f16191f739705faa020769",
      "code": "SUPERIOR-DBL",
      "category": {
        "de": "Superior Doppelzimmer"
      },
      "beds": 2,
      "facilities": ["shower", "toilet", "bath"],
      "images": [
        {
          "url": "https://spaportal-files.s3.eu-central-1.amazonaws.com/production/rooms/example.jpg",
          "thumbnailUrl": "https://spaportal-files.s3.eu-central-1.amazonaws.com/production/thumbnails/rooms/example.webp"
        }
      ],
      "description": {
        "de": "Luxurioses Zimmer mit Bad."
      },
      "lowestPrices": {
        "CZK": {
          "amountMinor": 3150000,
          "currency": "CZK",
          "currencyExponent": 2,
          "unit": "personPerNight"
        }
      },
      "bookingUrl": {
        "de": "https://reservierung.example.test?hotel=Pawlik&roomType=SUPERIOR-DBL"
      }
    }
  ],
  "pagination": {
    "limit": 25,
    "nextCursor": null,
    "hasMore": false,
    "total": 1
  }
}
```

### Remaining room type review points

Product should still confirm these details:

- Should top-level `/room-types` include compact hotel data by default, or only
  with `include=hotel`?
- Should `availableOnly=true` require both `dateFrom` and `dateTo`?
- Should `beds` be exact match only, or should API v2 also support `minBeds`?
- Should public room type lists include room types without currently valid
  price lists?
- Do we need `search` over localized `category` and `code` in the first release?

## Migration plan

Recommended implementation order:

1. Add shared API v2 helpers for auth, errors, IDs, localization, pagination, and
   money.
2. Keep API v1 auth helpers untouched.
3. Use `POST /api/v2/calendar/dates/bulk` as the first implemented endpoint for
   shared v2 auth, errors, ObjectId input, and money response behavior.
4. Add one low-risk read endpoint, such as `/api/v2/destinations`, as a reference
   implementation.
5. Add `/api/v2/room-types`.
6. Add contract tests for auth, localization, ObjectId scoping, parent-child room
   type scoping, and pagination.

For API v1 migration support, add Mongo `_id` values to selected API v1
responses first. API v1 should keep existing numeric `id` fields.
