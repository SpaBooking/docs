SpaPortal models hotel and room **services & amenities** as structured, filterable
data — not free-text prose — so you can filter ("hotels with a sauna and free
parking"), group amenities for display, and build machine-readable output (SEO
markup, channel feeds). The model has two parts:

1. **The amenity dictionary** — a small controlled vocabulary of every _possible_
   amenity, each with a stable `code`, a `category`, value typing, and localized
   labels. Fetch it once from `GET /api/v2/amenities`.
2. **Amenity values** — what a given hotel or room type actually offers, as a list
   of `code` + state objects on its `amenities` field.

Hotel and room payloads carry only `code` + state; the labels and grouping live in
the dictionary. So a client fetches the dictionary **once**, caches it, and joins
locally — keeping every other response lean.

## The amenity dictionary

`GET /api/v2/amenities` returns the full controlled vocabulary — a small reference
list, not paginated. Each entry:

| Field          | Meaning                                                                                                   |
| -------------- | --------------------------------------------------------------------------------------------------------- |
| `code`         | Stable machine key in `category.slug` form (e.g. `wellness.sauna`). Use it to filter and to resolve values. |
| `category`     | Grouping facet (e.g. `wellness`, `parking`, `connectivity`).                                              |
| `scope`        | Where it applies: `hotel`, `roomType`, or `both`.                                                         |
| `valueType`    | Shape of the value: `boolean` (present/absent) or `count` (a quantity, e.g. parking spaces).              |
| `supportsFree` | Whether the paid/free distinction is meaningful for this amenity.                                         |
| `label`        | Localized display name (`cs-CZ`, `de`, `en`, `ru`).                                                       |
| `mappings`     | Optional interop mappings to external standards — see [Interop &amp; mappings](#interop-and-mappings).    |

<Note>
  There is no single-select "enum" value type. A mutually-exclusive distinction —
  a room's view, say — is modeled as **multiple boolean codes** in one category
  (`view.sea`, `view.park`, `view.courtyard`) rather than one enum. That filters
  cleanly (`?amenities=view.park`, `?amenityCategory=view`) and handles a room
  that offers more than one option.
</Note>

Optionally narrow it by `scope` or `category`:

```bash
GET /api/v2/amenities                  # the whole dictionary
GET /api/v2/amenities?scope=hotel      # only hotel-level amenities
GET /api/v2/amenities?category=wellness
```

## Amenity values on hotels and room types

Hotels and room types carry an `amenities` array. Each item references a dictionary
`code` and describes that amenity's state for this specific hotel or room:

| Field       | Meaning                                                                                                       |
| ----------- | ------------------------------------------------------------------------------------------------------------ |
| `code`      | References an `Amenity.code` in the dictionary.                                                               |
| `available` | Tri-state: `true` present, `false` absent, `null` unknown. Responses omit pure unknowns, so `null` is rare.   |
| `free`      | `true` included, `false` paid, `null` n/a. Only meaningful when the amenity's `supportsFree` is `true`.       |
| `quantity`  | A count, when the amenity's `valueType` is `count` (e.g. 40 parking spaces).                                  |
| `condition` | Conditional availability: `seasonal`, `dayOfWeek`, `underConstruction`, or `null` when unconditional.        |

Only **present or conditional** amenities are returned — pure unknowns are omitted —
so a `code` that is absent from the array means "not advertised," not "definitely
absent."

```json Hotel with amenities
{
  "id": "66f16191f739705faa020001",
  "name": { "cs-CZ": "Pawlik", "de": "Pawlik-Aquaforum" },
  "stars": 4,
  "amenities": [
    { "code": "wellness.sauna", "available": true, "free": true },
    { "code": "connectivity.wifi", "available": true, "free": true },
    { "code": "parking.parking", "available": true, "free": false, "quantity": 40 },
    { "code": "pools.indoor_pool", "available": true, "condition": "seasonal" }
  ]
}
```

To display these, resolve each `code` against the dictionary you fetched from
`GET /api/v2/amenities` — that is where the localized `label` and `category` live.

### Scope: hotel vs. room type

Each dictionary entry has a `scope`:

- `hotel` — property-level facilities (parking, an outdoor pool, 24h reception).
- `roomType` — in-room features (air conditioning, balcony, minibar).
- `both` — applies at either level (Wi-Fi; a sauna a room may have privately).

A `hotel`-scoped amenity only appears in a hotel's `amenities`; a `roomType`-scoped
one only in a room type's. A `both`-scoped amenity can appear in either.

```json Room type with amenities
{
  "id": "66f16191f739705faa020003",
  "hotelId": "66f16191f739705faa020001",
  "code": "SUPERIOR-DBL",
  "beds": 2,
  "amenities": [
    { "code": "comfort.air_conditioning", "available": true },
    { "code": "connectivity.wifi", "available": true, "free": true }
  ]
}
```

## Filtering by amenity

Both `GET /api/v2/hotels` and `GET /api/v2/room-types` accept two amenity filters:

- `amenities` — comma-separated `code`s; returns only results that have **all** of
  them available (AND semantics).
- `amenityCategory` — returns results that have **any** available amenity in that
  category.

```bash
# Hotels with BOTH a sauna AND parking
GET /api/v2/hotels?amenities=wellness.sauna,parking.parking

# Hotels with any wellness amenity
GET /api/v2/hotels?amenityCategory=wellness

# Room types with air conditioning
GET /api/v2/room-types?amenities=comfort.air_conditioning
```

<Note>
  Keep first-class typed filters (`stars`, `beds`) separate from amenities — they
  are dedicated query parameters, not amenity `code`s.
</Note>

## Interop and mappings

Each dictionary entry can carry a `mappings` object — the same amenity expressed in
external standards (`schemaOrg`, `google`, `mews`). SpaPortal keeps **one canonical
amenity model**; those standards are output formats you render _to_, not the source
of truth. Use `mappings` to build machine-readable markup without hard-coding your
own translation table.

For example, one amenity value plus its dictionary entry…

```json
// dictionary entry (from GET /api/v2/amenities)
{ "code": "wellness.sauna", "label": { "en": "Sauna" }, "mappings": { "schemaOrg": "Sauna" } }

// the hotel's value
{ "code": "wellness.sauna", "available": true }
```

…lets you emit schema.org JSON-LD for SEO:

```json
{
  "@type": "LocationFeatureSpecification",
  "name": "Sauna",
  "value": true
}
```

`mappings` is filled incrementally, so a key is `null` when no mapping exists yet.

## Putting it together

1. **Fetch the dictionary once:** `GET /api/v2/amenities`. Cache it — it changes rarely.
2. **Filter the catalog:** `GET /api/v2/hotels?amenities=wellness.sauna&amenityCategory=wellness`.
3. **Render each result:** for every `amenities[].code`, look up the localized `label`
   and `category` in the cached dictionary, and present state from `available`,
   `free`, `quantity`, and `condition`.

The dictionary is the single source of truth for labels and grouping; hotel and room
payloads stay lean by carrying only `code` + state.
