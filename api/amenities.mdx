Hotel and room type amenities use the same structured contract in API v2.
Each category identifies its resource with `scope: "hotel"` or `scope: "roomType"`.
The dictionary returns both hotel and room type amenities by default.
Use `scope=hotel` or `scope=roomType` to filter it to one resource type.

There are two related resources:

1. **The amenity dictionary** lists every amenity SpaPortal can assign within the requested scope.
   Each group contains a [category](/api/objects/amenity-category) with `scope`,
   `code`, and a localized `label`, alongside an `amenities` array whose entries
   contain a stable `code`, localized `label`, and supported detail fields.
2. **Selected amenity values** are grouped by category in
   `hotel.amenityCategories` or `roomType.amenityCategories`.
   Categories without assigned amenities are omitted. Values inside each
   group's `amenities` array store the amenity's structured details and a
   localized guest note when the dictionary includes the `note` detail kind.

<Note>
  These responses serve different purposes. `GET /api/v2/amenity-categories`
  returns every category and amenity in the requested scope. Hotel and room
  type endpoints return only assigned amenity values.
</Note>

## Amenity dictionary

<Card title="GET /api/v2/amenity-categories" icon="square-terminal" href="/api/v2/reference/amenity-categories/list-the-amenity-dictionary" horizontal>
  Fetch the full amenity dictionary.
</Card>

`GET /api/v2/amenity-categories` returns every category and amenity available
in the requested scope, whether or not a particular hotel or room type uses it. The complete list is
returned in one response and is not paginated. Use
[`Accept-Language`](/api/localization) to select the locale keys returned in
localized fields.

Amenities whose `detailKinds` include `options` also carry an `options` array
with every supported choice and its localized label.

### Scope and category identity

| Request | Result |
| --- | --- |
| `GET /api/v2/amenity-categories` | Both scopes: hotel categories, then room type categories |
| `GET /api/v2/amenity-categories?scope=hotel` | Hotel categories only |
| `GET /api/v2/amenity-categories?scope=roomType` | Room type categories only |

The pair `category.scope` + `category.code` identifies a category. Codes have no
resource prefix: for example, a room type uses `{ "scope": "roomType", "code": "view" }`.
Both scopes have a category named `accessibility`; keep them separate when
indexing categories or joining selected values to the dictionary.

`scope` is always present on categories, including assigned values and responses
with `expand=amenityLabels`. The query parameter only filters the dictionary;
it does not change the shape of its entries. An empty or unknown scope,
including `all`, returns `400`.

### Updating an existing integration

If your integration uses the dictionary only for hotels, send
`GET /api/v2/amenity-categories?scope=hotel` before the API upgrade. The
previous contract already accepts this query, so the request keeps returning
only hotel definitions across the change.

Older responses do not include `category.scope`. During the transition,
use `category.scope ?? "hotel"` for a dictionary explicitly requested with
`scope=hotel`, and for assigned categories on hotel resources. Do not apply
that fallback to a combined dictionary or to embedded room type categories.
Use the known resource scope for each resource, and key any shared category
index by both scope and code.

Refresh cached dictionaries when `X-SpaPortal-Amenities-Version` changes.
For room type integrations, update category lookups to the unprefixed codes;
only query filters retain the old `room_*` aliases.

### Examples by scope

Fetch both scopes together, or filter the dictionary to the resource you need.
Match selected values to dictionary categories using both `scope` and `code`.
The examples request Czech and English labels. Dictionary responses below are
excerpts; the API returns the complete dictionary for the requested scope.
Resource excerpts show only `amenityCategories`.

Both scopes follow the same label rules: dictionary entries always include
labels, assigned categories include `scope` and `code` by default, and `expand=amenityLabels`
adds labels to categories, amenities, and any selected options. Replace
`{hotelId}` and `{roomTypeId}` with the resource IDs returned by the API.

### Detail kinds

`detailKinds` tells clients which parts of an [Amenity value](/api/objects/amenity-value)
are included:

| Kind | Value field |
| --- | --- |
| `proximity` | `proximity` and `proximityMeters`; the distance is non-null only when `proximity` is `nearby` |
| `access` | `access` |
| `options` | amenity-specific choices; the entry carries an `options` array of every valid choice with its localized label |
| `opening_hours` | `openingHours` |
| `note` | localized `note` |

An empty `detailKinds` array identifies a presence-only amenity. By default,
its selected value contains only `code`, for example
`{ "code": "wheelchair_access" }`. With `expand=amenityLabels`, it also
includes its localized `label`.

## Room type amenities

Fetch `GET /api/v2/amenity-categories?scope=roomType` for the room type dictionary.
It contains 38 presence-only amenities in five categories. Each entry has
`detailKinds: []` and has no `options` or `notePlaceholder`.

| Code | English label |
| --- | --- |
| `bathroom` | Bathroom |
| `equipment` | Room |
| `accessibility` | Accessibility |
| `view` | View |
| `kitchen` | Food and drink |

Room type and hotel amenity values use the same response structure, but each
scope has its own categories and dictionary. A room type response includes only
categories with at least one amenity assigned to that room type. For example,
a room type without kitchen amenities omits `kitchen` from its
`amenityCategories`; the complete `scope=roomType` dictionary still lists that
category. Returned categories and amenities follow dictionary order.

The room type tab above shows how a dictionary entry becomes an assigned value.

Request `expand=amenityLabels` on room types to inline localized labels. On
hotels, `expand=roomTypes,amenityLabels` also includes labels on embedded rooms.

## Caching

The dictionary version changes when SpaPortal releases new amenities, categories,
options, labels, or a new response shape. Within API v2, published hotel and room
type codes are not renamed or removed. Refresh cached dictionaries when the
version changes.

Recommended flow:

1. Fetch `GET /api/v2/amenity-categories` once without `scope` to cache both
   dictionaries. Omit `Accept-Language`, or send `Accept-Language: *`, to cache
   every locale key. Node.js `fetch` sends `*` when you do not set the header.
   Store the response with its `ETag` and `X-SpaPortal-Amenities-Version` headers.
   You can also cache each scope separately using the query parameter.
2. Hotel and room type responses return the current version in
   `X-SpaPortal-Amenities-Version`. One version covers both dictionaries.
   When it changes, refetch the combined dictionary or each separately cached scope.
3. To revalidate, repeat the request with the same `scope` selection (including omission) and
   `Accept-Language`, and add `If-None-Match: <cached ETag>`. The API returns
   `304` with no body while your copy is current.
4. If a response contains an unknown amenity code, skip it in display and
   refresh the dictionary for that scope.

Browser clients on allowed origins can send `If-None-Match` and read the
`ETag` and `X-SpaPortal-Amenities-Version` response headers directly.

Responses carry `Cache-Control: private, max-age=3600`. The `ETag` differs by
scope selection (combined, hotel, or room type) and requested locale set; the version header covers both scopes and all
locales.

## Selected amenities on a hotel

Every v2 [Hotel](/api/objects/hotel) response groups assigned amenities by
category. Only categories containing at least one assigned amenity are returned.
An absent code means the amenity is not offered or has not been advertised.

By default hotel categories carry `scope: "hotel"` and `code`; amenities and
selected options carry `code`. Labels are omitted. Fetch the dictionary once (it is
small and cacheable) and look up every localized label there. This keeps hotel
responses small and the labels in one place.

If you would rather have a self-contained response, add
[`expand=amenityLabels`](/api/expand) to the hotel request. It inlines the
localized `label` on each category, amenity, and option, so no dictionary lookup
is needed.

```json Hotel amenity values
{
  "amenityCategories": [
    {
      "category": { "scope": "hotel", "code": "wellness" },
      "amenities": [
        {
          "code": "aquapark",
          "proximity": "nearby",
          "proximityMeters": 250,
          "access": "included",
          "openingHours": {
            "continuous": false,
            "blocks": [
              {
                "days": ["monday", "tuesday", "wednesday", "thursday", "friday"],
                "from": "09:00",
                "to": "21:00"
              }
            ]
          }
        },
        {
          "code": "sauna",
          "proximity": "in-hotel",
          "proximityMeters": null,
          "access": "included",
          "options": [{ "code": "finnish" }, { "code": "steam" }],
          "openingHours": {
            "continuous": false,
            "blocks": []
          }
        }
      ]
    }
  ]
}
```

To display this hotel's amenities, join each code to the dictionary:
`category.scope` + `category.code` → `data[].category`, `amenities[].code` →
`data[].amenities[]`, and each `options[].code` → that amenity's `options` in
the dictionary. All three carry the localized labels. Or request
`expand=amenityLabels` to receive those labels inline on the hotel and skip the
join.

Structured details use the following enums:

- `proximity` — where the amenity is located relative to the hotel:
  - `in-hotel` — inside the hotel building.
  - `connecting` — in an adjacent building linked by an internal passage.
  - `nearby` — a short distance away; `proximityMeters` gives the approximate
    distance.
- `access` — whether using the amenity costs extra:
  - `included` — covered by the stay price.
  - `conditional` — included subject to stated conditions.
  - `paid` — available for an additional charge.
- `options`: amenity-specific choices selected for the hotel, by `code` only.
  The dictionary lists every available choice with its label; hotel responses
  return only the selected codes.
- opening-hour days: `monday`, `tuesday`, `wednesday`, `thursday`, `friday`,
  `saturday`, `sunday`

Apart from `code`, an amenity value includes only the fields mapped from its
entry's `detailKinds` under `data[].amenities[]`. When a declared field is not
filled, scalar fields are `null`, arrays are empty, opening hours are
`{ "continuous": false, "blocks": [] }`, and requested localized note values
are `null`.

`access` also represents whether an amenity carries an additional charge:
`included` means no additional charge, `conditional` means inclusion depends on
the stated conditions, and `paid` means an additional charge applies.

## Filtering hotels

[`GET /api/v2/hotels`](/api/v2/reference/hotels/list-hotels) accepts:

- `amenities`: comma-separated amenity codes. A hotel must have **all** listed
  codes (AND semantics).
- `amenityCategory`: a category code. A hotel must have at least one amenity in
  that category.

```bash
# Hotels with both a sauna and parking
GET /api/v2/hotels?amenities=sauna,parking

# Hotels with any pool or wellness amenity
GET /api/v2/hotels?amenityCategory=wellness
```

## Filtering room types

`GET /api/v2/room-types` accepts the same filters against the room type dictionary:

- `amenities=balcony,bathtub` requires both amenities.
- `amenityCategory=view` requires at least one amenity from that category.

Legacy room category filters (`room_bathroom`, `room_equipment`,
`room_accessibility`, `room_view`, `room_kitchen`) remain accepted as deprecated
aliases. No removal date has been announced. Use the unprefixed codes for new requests. Responses always use
unprefixed category codes. The resource endpoint determines the filter scope;
for example, `amenityCategory=accessibility` on `/room-types` searches room
accessibility, while the same filter on `/hotels` searches hotel accessibility.

An empty `amenityCategory=` is treated as an omitted filter on both resource
endpoints. This preserves existing filter behavior; an empty dictionary
`scope=` is invalid and returns `400`.

Unknown amenity or category codes return `400`. Hotel filters use only the hotel
dictionary. To find hotels through room amenities, filter room types and collect
their `hotelId` values.
