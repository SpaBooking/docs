Use these conventions when you build request payloads and parse responses.

## Protocol and format

Send API requests over HTTPS.

Request and response bodies use JSON when an endpoint accepts or returns a body.
Send JSON request bodies with:

```http
Content-Type: application/json
```

Use query parameters for filters on `GET` endpoints. Use request bodies for
`POST` endpoints that create resources or accept larger payloads.

## Paths

API paths are grouped by major version:

```txt
/api/v1
/api/v2
```

Resource paths use plural nouns where possible.

Examples:

```txt
/hotels
/visit-types
/calendar/dates
```

## Field names

API v1 uses `snake_case` for many query parameters and response fields.

Examples:

```txt
date_from
date_to
visit_type_id
room_type_id
```

The target API v2 contract uses `camelCase` for query parameters and JSON
fields.

Examples:

```txt
dateFrom
dateTo
visitTypeId
roomTypeId
```

## IDs

API v1 uses legacy numeric IDs in public responses and request parameters.

API v2 uses ObjectId string values as public `id` values. It does not expose
legacy numeric API v1 IDs in the target contract.

ObjectId values are 24-character hexadecimal strings.

## JSON responses

Most successful responses return JSON.

List endpoints can return an array directly in API v1:

```json
[
  {
    "id": 1
  }
]
```

The target API v2 contract wraps list data with pagination metadata:

```json
{
  "data": [],
  "pagination": {
    "hasMore": false,
    "nextCursor": null,
    "total": 0
  }
}
```

Endpoint pages are the source of truth for each response shape.
