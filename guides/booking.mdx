Use catalog endpoints to build selection screens. Then validate availability and price before you create a booking.

This flow uses **API v1**, under `https://spaportal.cz/api/v1`, with
`Authorization: Bearer <API_KEY>`. All paths below include the version. For
parameters and response schemas, use the [API v1 reference](/api/v1).

API v2 does not provide a replacement booking-creation endpoint. Use the numeric
IDs returned by v1 for this flow; do not pass v2 hex `id` values as v1 request IDs.

## Recommended flow

1. Fetch destinations with `GET /api/v1/destinations`.
2. Fetch hotels with `GET /api/v1/hotels`.
3. Fetch visit types with `GET /api/v1/visit-types`.
4. Fetch room availability with `GET /api/v1/calendar/dates`.
5. Fetch possible checkout dates with `GET /api/v1/calendar/checkouts`.
6. Fetch the final price with `GET /api/v1/price`.
7. Create a booking with `POST /api/v1/booking`.

## Opening the calendar

On the first calendar load, call `GET /api/v1/calendar/dates` with a hotel, visit type, and `guests`, but without `date_from` and `date_to`. A room type is optional. The response starts at the first month that contains a stay you can actually book — one where every occupied night of the minimum stay has both remaining capacity and a price, and the check-out date has a price — instead of at the current month.

Without a room type, SpaPortal checks the hotel's room types that match `guests`. The complete stay must fit into one room type. SpaPortal never combines capacity from different room types to construct a stay. Always send `guests` on this request so the search uses the intended room occupancy.

If no fully bookable stay is found in the 24-month search horizon, the endpoint keeps its normal non-empty fallback calendar. A priced date that meets the visit type's starting-day and date-range rules remains `selectable`, even when the complete stay will be `ON_DEMAND`. Disable the check-in action only when `selectable` is `false`; use the booking configuration response to distinguish confirmable stays from requests.

That way you do not have to page through empty months to find the first date a guest can pick. Once the guest navigates the calendar, send `date_from` and `date_to` for the range you want. Sending either date disables the automatic first-bookable-month search. A `date_from` in the past is clamped to the current date.

After the guest chooses a selectable check-in date, call `GET /api/v1/calendar/checkouts` with the hotel, room type, and visit type. The endpoint returns check-out dates that satisfy the visit type rules and have continuous pricing. Capacity does not remove checkout choices because a valid priced stay can continue as an `ON_DEMAND` request. The check-out date is not charged and does not consume capacity, but it must be covered by the continuous pricing range.

## Booking configuration

Use `GET /api/v1/booking` when you need SpaPortal to match a partial selection by names.

For example, you can pass a destination name, hotel name, visit type name, room type category, and date range. The response returns matching objects, availability, and either a final price or lowest price.

## Binding bookings

When `binding_booking` is `true`, the billed contact must include an address.

Use `binding_booking: false` for non-binding booking requests.
